## Goal

Three query shapes that are easy to write compile to a full scan of a stored
relation. Each one put a full scan inside MindGraph's exclusive ingestion write
in November 2026: 55–157 s per page before the queries were rewritten by hand
and a CI lint was added to stop them coming back
(`mindgraph-rs/scripts/cozo-query-lint.sh`, cases 2 and 3; the second trap has
no lint). Compile these shapes to keyed access in the engine, with identical
results, so no consumer needs the rewrites or the lint.

| Shape | Example | Plan today | Target |
|---|---|---|---|
| T1 trailing unification | `*node{uid}, uid = $u` | `load_stored :node` with the unification as a post-filter: full scan | point lookup on `uid` |
| T2 key plus non-adjacent value column | `*edge{from: f, to: t}, *node{uid: t, tombstone_reason: 'deleted'}` | `stored_mat_join`: the whole `node` relation is materialized | point lookup on `uid`, then a check of `tombstone_reason` on the found row |
| T3 equality with a rule-bound variable | `f[x], *node{uid: u, name: n}, u == x` | cartesian `stored_prefix_join` plus `filter eq(u, x)`: full scan per left row | point lookup on `uid` per left row |

## Decisions

**D0 — Preserve the baseline pipeline; optimize locally at compilation.**
Keep normalization (including fork #1's `push_equality_filters_to_bindings`),
greedy/written ordering, well-ordering, stratification and magic-set rewriting
unchanged. D1/D3 run in `compile_magic_rule_body`, immediately before compiling
a positive stored atom, after resolving its handle through
`get_relation_for_read`. Inspect the remaining `MagicAtom` body for eligible
later equalities. Use the handle's column types, key arity and secondary-index
mappings; do not widen `resolve_key_arities` or add an earlier schema lookup.
Normal relation-resolution and ACL errors retain their existing behavior.

The baseline is the current compiler with D1/D2/D3 disabled, including fork #1.
Do not rerun ordering or magic rewriting after inserting a binding. Add it to the
current left-hand RA stream directly before the target relation, retaining the
original equality at its original position as a residual check. This changes
neither the order of positive atoms nor their magic adornments. In particular,
it does not move an expression ahead of unrelated earlier rows or generators.

**D1 — Bind a constant immediately before its stored producer (T1).**
A later single-valued `MagicAtom::Unification` (`one_many_unif == false`) or
`Predicate` `eq(v, g)` / `eq(g, v)` may supply an additional binding only when:

1. `v` occurs in exactly one positive stored atom in this compiled body, the
   target. It is absent from the compiler's bound set immediately before that
   atom. Account for **all** earlier producers: single-valued `=`, multi-valued
   `in`, relations, rules, searches and magic input bindings. An earlier
   producer makes the candidate ineligible even if it appears to bind an
   equivalent value. Later unifications retain their original filter behavior.
2. `g` is constant, or safely folds to one. Inspect the original expression
   before folding: functions must be deterministic (`rand_*` and `now` are
   excluded; add determinism metadata to the op table). Fold a copy; on an
   error discard the candidate and leave the expression untouched. Do not
   alter the existing predicate-normalization policy in this batch.
3. The value is non-numeric, or its numeric variant exactly matches the target
   column's declared `Int`/`Float` type. Numeric constants on `Any` and
   cross-type numeric constants are ineligible. Retain the conservative
   exclusion for a numeric target variable also used by any rule or search
   atom, even though this placement no longer changes magic adornments.
4. The target is a plain stored read. Validity-selected and transaction-time
   reads are excluded, as are bindings to validity/transaction-time columns.
5. The proposed access passes D1a below. A value column is eligible if it
   supplies a leading constraint on a usable secondary index; being outside
   the primary key is not itself a rejection reason.

Consider candidates in body order. For a composite prefix, consider the eligible
constants for that atom as one group, using only the pre-insertion bound set;
choose the first eligible equality per variable. Do not infer constants through
aliases, use a candidate as another candidate's producer, or enumerate subsets
when a group is rejected. Retain every original equality, including conflicting
ones. Rejection leaves the baseline compilation of that atom intact.

**D1a — Guard the actual access, including secondary indexes.** Before adding
bindings, derive the target atom's baseline and candidate physical access with
the same selection logic that compilation uses (`choose_index`, its mapper and
base-fetch requirement, and D2's join classification). Factor that logic into a
shared helper; do not maintain a parallel approximation based only on key arity.
Include both index access and any base-row fetch in the descriptor.

Accept only a non-empty keyed prefix or a full-key point lookup, with no new
materialization or unkeyed scan at either step. If the baseline already uses a
keyed access, retain its physical index and all its leading seek constraints
(the prefix may grow), or replace it with a full-primary-key point lookup. Do
not exchange one partial index prefix for another without a cost model. Reject
any candidate that makes an index-only access require a new base-row fetch.
Compare structural access, not a count of `load_stored` labels: those labels
also appear as the children of seeks.

D1/D3 leave other atom occurrences at their baseline order and access (D2 may
independently improve their join operator): after the target, the set of bound
source variables is identical to the baseline. Tests
must check this across the entire compiled body, including repeated relation
names and index-to-base joins. This provides invariant 3 without compiling a
second whole query or allowing a new seed to influence greedy ordering.

**Compatibility decision.** Preserve fork #1's existing `==` conversion,
including value-column and secondary-index cases. This resolves former open
question 3 in favor of compatibility. Removing its unindexed materializations
is separate work, not required to fix T1–T3. D1 handles eligible equalities still
present after that pass; it must not undo an existing binding or index choice.

**D2 — Seek on the full key and check the rest (T2).** For a positive join on
a plain (non-temporal) stored relation, compute once, in one function used by
both dispatch (`ra.rs:2683`) and `::explain` labelling (`ra.rs:2584`):
`seek_len`, the length of the leading run `0..n` among the sorted right-side
join positions, cut at the key length. If `seek_len` equals the key length,
use a point lookup: build the key from the run positions only, and check every
other join pair on the found row (`point_lookup_join` already does the check).
This is MySQL's `eq_ref` and the rule-based Oracle optimizer's "single row
by primary key": at most one right row per left row, the one case a stat-free
planner can choose without guessing cardinality. If the positions are exactly
`0..n`, nothing changes. Otherwise keep `materialized_join`. Inside `prefix_join`, the point-lookup branch is taken when
`seek_len` equals the key length, not when the number of positions reaches it,
and the bounds slice starts at `seek_len`. `::explain` labels the
full-key case `stored_point_join` (prefix scans keep `stored_prefix_join`),
lists the seek pairs in `joins_on`, and lists the checked pairs separately in
the existing output, so a plan shows which columns are sought and which are
checked, as PostgreSQL's `Index Cond` and `Filter` do. Validity and
bitemporal relations, and all negated joins, keep today's gates in batch 1.

**D3 — Bind a rule-produced value at the same local boundary (T3).**
For a remaining `eq(u, x)` / `eq(x, u)`, add `u = x` immediately before the
positive stored atom producing `u`, using D0/D1a. The declared column type for
`u` must be non-numeric and not `Any`. Apply D1's producer and temporal guards:
`u` is unbound before that atom and occurs in exactly one positive stored atom;
`x` must already be bound in the **baseline** compiler state at that boundary.
The alias adds one value per existing left row and retains the original equality.

For T3, `f[x]` already precedes `*node{uid: u, name: n}`, so the alias enables
a seek without changing either atom's position or the adornment of `f`. If `x`
becomes available only after the stored atom, leave the equality unchanged;
do not hoist a pending unification to the body front or rerun `well_order_body`.
A variable occurring only in negation remains ineligible, preserving the
baseline unsafe-negation/unbound-variable error. Constant propagation through
aliases and chained equality inference remain out of scope.

**D4 — A test-only switch, no user option.** Behind `test-hooks`, one flag
disables D1, D2 and D3 together. Both arms retain existing fork #1, normalization,
ordering and magic rewriting. Run deterministic equivalence fixtures with the
flag on and off, comparing aggregate values as well as ordinary rows. Test
volatile expressions through unchanged plan placement/evaluation behavior, not
by demanding equal random draws or timestamps from independent executions.
`:reorder written` still controls join order only; the local access pass applies
in both modes. No public `:pushdown off` option is added.

## Invariants

1. Every rewrite returns exactly the rows the unrewritten plan returns, on all
   backends, including aggregate multiplicity, `Int`/`Float` cross-type values
   and `Null`. Existing producers and volatile evaluation behavior are preserved.
2. A query that compiled before compiles after; a query that failed with an
   unbound-variable or unsafe-negation error still fails.
3. Relative to the baseline including fork #1, no atom occurrence gains a
   materialized join or an unkeyed full scan. Existing secondary-index seeks
   remain keyed; D1/D3 preserve positive-atom order and magic adornments.
4. No seek prefix includes a validity or transaction-time column.
5. The `::explain` label of a stored join names the operator that runs, and
   the output separates sought pairs from checked pairs.
6. Plans stay stat-free and deterministic.

### Review regression fixtures

These fixtures are mandatory for the on/off suite. The baseline counterexamples
were reproduced on November 13 with the existing local Python binding reporting
0.19.2: R1/R2 results on mem, SQLite and RocksDB, and R3/R4 plans on SQLite.
Manually positioned bindings demonstrate the proposed placement only; they do
not exercise an implementation of D0–D4. Use separate databases per fixture.
The validation run passed 27 result assertions (nine per backend) and four
SQLite plan assertions, including T1/T3 local-placement controls and an
unrelated duplicate-producing generator. Binding binary SHA-256:
`599bb1cda04f01d9a7aa472b9c93664204abc45fbc744da1d3a4489383860e25`.
This identifies the tested artifact, not a claimed source-build provenance.

**R1 — Preserve an earlier scalar producer.**

```text
:create m {k: Int}
?[k] <- [[5]] :put m {k}
?[k] := k = 5.0, *m{k}, k = 5
```

Expected rows are `[]` with the optimization on and off. The compiler sees `k`
already bound before `*m`, so it must not add a binding from the trailing `k = 5`.
The rejected global-hoist form `k = 5, k = 5.0, *m{k}` returns `[[5]]`.
Also test earlier non-constant `k = x` and magic input bindings: producer
eligibility depends on the actual bound set, not whether the producer is literal.

**R2 — Preserve `in` multiplicity.**

```text
:create s {k: String}
?[k] <- [['a']] :put s {k}
?[count(k)] := k in ['a', 'a'], *s{k}, k = 'a'
```

Expected rows are `[[2]]` in both arms. Global hoisting changes the `in` generator
to a membership filter and returns `[[1]]`. Cover `sum`/`collect` as well as
`count`, duplicate and empty lists, an expression-produced list, and an unrelated
earlier generator whose multiplicity must survive an eligible local binding.

**R3 — Retain secondary-index access.**

```text
:create s {k: String => name: String}
::index create s:by_name {name}
::explain { ?[k] := *s{k, name}, name == 'a' }
```

Both arms must retain a keyed prefix access to `:s:by_name`; this is legacy
fork #1 behavior. A streaming filter on `:s` is a failure even if rows agree.
Add a non-covering variant (`s{k => name, payload}` projecting `payload`),
composite secondary-index prefixes and an index on a non-leading primary-key
column. Pin the index-to-base lookup as well as the initial index seek.
For a new trailing `name = 'a'`, require the same indexed access when eligible.
Without an index, that new `=` remains a filter and legacy `==` is unchanged.
Include a competing-index case where binding primary-key position 0 would make
`choose_index` abandon an existing secondary prefix for a partial primary prefix:
D1a must reject it. A complete primary-key lookup remains an allowed replacement.

**R4 — Preserve the other joins.**

```text
:create a {x: String => y: String}
:create b {y: String => z: String}
:create c {k: String => z: String}
::explain { ?[x] := *a{x,y}, *b{y,z}, *c{k,z}, k = 'pick' }
```

Baseline access is `a scan -> b point -> c materialize`. The new plan must
keep that atom order and `b`'s point access, inserting `k = 'pick'` immediately
before `c` so `c` becomes a point lookup plus its `z` check. Reject the previous
proposal's `c point -> b materialize -> a materialize` plan. Test the full body
under greedy, written and `:limit` modes, on empty and populated relations;
also test repeated relation names so occurrence-level checks cannot collapse
two different accesses into one. Result and aggregate comparisons run on all
three backends. Pin the recursive workload's magic adornments as well.
The pre-implementation model uses `:reorder written` with
`*a{x,y}, *b{y,z}, k = 'pick', *c{k,z}, k = 'pick'` to hold the baseline
order; SQLite shows zero materializations. The eventual compiler must obtain
this result under greedy mode itself, without requiring the query option.

### Prior art for the review resolution

Sources checked November 13, 2026. These support the design constraints; the
specific eligibility rules above follow from Mnestic's compiler and probes.

- SQLite treats leading index constraints and index coverage as physical access
  properties, and documents separate controls for join order. This supports
  checking the selected index and preserving the chosen order rather than
  assuming a locally useful equality improves the whole query.
  [SQLite optimizer overview, sections 2, 7.1.2 and 9](https://www.sqlite.org/optoverview.html).
- PostgreSQL documents how leading B-tree equalities limit the scanned range,
  while later checked conditions need not do so. This supports D1a's distinction
  between retained seek constraints and residual checks.
  [PostgreSQL 18 multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html).
- PostgreSQL also explains that equivalent join orders can have very different
  costs. Preserving the existing order is our conservative stat-free choice;
  this spec does not import PostgreSQL's cost model or planner settings.
  [PostgreSQL 18 explicit joins](https://www.postgresql.org/docs/18/explicit-joins.html).

## Layering ruling

Engine only. MindGraph needs no change; its lint cases 2 and 3 can become
advisory once production runs the release, which is a MindGraph decision.

## Rejected alternatives

- **Seek on a partial key run and check the rest per row** (the first draft's
  D2). A per-left-row scan over a leading-key range is not output-sensitive:
  with few distinct leading values it costs left rows × range size, where
  `materialized_join` costs one sort and a binary search per row. Without
  statistics the engine cannot tell the cases apart. T2 needs only the full key.
  Prior art agrees: SQLite seeks partial prefixes on a default guess of 10
  rows per leading value, and its query-planner case study shows that guess
  failing on a leading column with over 10,000 duplicates; Oracle's rule-based
  optimizer took any leading portion and was deprecated partly for choosing
  indexes over faster full scans.
- **Hoisting new bindings to the body front.** The review counterexamples show
  that this can replace `=`/`in` producers and reseed greedy ordering onto
  non-key joins even when the target has a leading-key equality. Compile the
  binding locally after ordering and magic rewriting instead.
- **Restricting legacy `==` to primary-key columns.** This removes working
  secondary-index seeks. Keep fork #1 and test its indexed value-column paths.
- **Compiling two whole queries and choosing by operator counts.** Counts can
  hide which relation or index regressed, and duplicated normalization/magic
  work is unnecessary. Freeze that pipeline and compare the target's actual
  physical access before constructing its RA fragment.
- **Substituting `x` for `u` in the stored atom with an alias** (the first
  draft's D3). A local non-constant unification uses existing compiler
  machinery without rewriting atom arguments or changing magic adornments.
- **Coercing a cross-type numeric constant to the column type** (`5.0` to
  `Int(5)` on an `Int` key). `op_eq` is not transitive across `Int` and
  `Float`: above `2^53` several `Int` keys equal one `Float`, so one seek
  cannot return them all. PostgreSQL keeps `float8` and `numeric` in separate
  operator families for the same reason.
- **Batched key lookups in batch 1.** MySQL, TiDB and CockroachDB batch the
  keys of many left rows into one fetch, and the engine has
  `StoreTx::multi_get`. T2's left side is small in MindGraph's queries (the
  edges of one page), so batch 1 does one `get` per left row and the T2
  benchmark records it against `multi_get`; batching follows if the numbers
  call for it.
- **A Db-level disable option.** Prior art keeps a switch for diagnosing plan
  regressions; the stat-free plans are visible in `::explain` and pinned by
  tests, so a test-only switch covers the differential-testing need without a
  new public option.
- **Cost-based choice between prefix and materialized join.** The engine has
  no statistics, and the plans are stat-free by design. A full-key match is
  always a point lookup, which is what D2 adds.
- **Converting numeric equalities without the declared-type check.** Changes
  results for cross-type values (verified current state).
- **A warning instead of a rewrite.** Warnings move the burden to every
  consumer; the shapes are the natural way to write the queries.
