## Goal

Three query shapes that are easy to write compile to a full scan of a stored
relation. Each one put a full scan inside MindGraph's exclusive ingestion write
in November 2026: 55–157 s per page before the queries were rewritten by hand
and a CI lint was added to stop them coming back
(`mindgraph-rs/scripts/cozo-query-lint.sh`, cases 2 and 3; the second trap has
no lint). Compile these shapes to keyed access in the engine, with identical
results, so no consumer needs the rewrites or the lint.

| Shape | Example | Plan today | Target |
|---|---|---|---|
| T1 trailing unification | `*node{uid}, uid = $u` | `load_stored :node` with the unification as a post-filter: full scan | point lookup on `uid` |
| T2 key plus non-adjacent value column | `*edge{from: f, to: t}, *node{uid: t, tombstone_reason: 'deleted'}` | `stored_mat_join`: the whole `node` relation is materialized | point lookup on `uid`, then a check of `tombstone_reason` on the found row |
| T3 equality with a rule-bound variable | `f[x], *node{uid: u, name: n}, u == x` | cartesian `stored_prefix_join` plus `filter eq(u, x)`: full scan per left row | point lookup on `uid` per left row |

## Decisions

**D0 — Schema before the pushdown.** `convert_to_well_ordered_rule`
(`reorder.rs:135`) resolves, for every stored relation in the body, its key
arity and the declared type of each column, before
`push_equality_filters_to_bindings` runs and in both reorder modes. The
pushdown and the greedy reorder take this view as an argument; the cache
widens from key arity to key arity plus column types. A relation that cannot be
resolved gets no rewrite.

**D1 — Hoist an equality onto a leading key position (T1).** The pushdown
moves an equality to the front of the body as a unification when all of these
hold:

1. It is a `NormalFormAtom::Unification` with `one_many_unif == false`, or a
   `Predicate` `eq(v, g)` as converted today.
2. Its right-hand side, after partial evaluation, is an `Expr::Const`
   (parameters are constants by this stage).
3. The variable is bound by exactly one positive stored atom, and no earlier
   positive atom in the body binds it.
4. After the hoist, the positions of that atom bound by hoisted constants form
   a non-empty run `0..n` of its key, so the atom compiles to a seek.
5. The constant is non-numeric; or it is numeric with the same variant (`Int`
   or `Float`) as the declared type of the column, and the variable appears in
   no rule application (positive or negated) and no search atom. A variable a
   derived rule also binds is treated as type-unknown, because the magic-set
   rewrite compares it with `op_eq` inside that rule.

Anything else stays where it is. The existing `==` conversion gets the same
conditions, so `name == 'x'` on a value column goes back to a streaming
filter instead of `stored_mat_join`, and `t == 5` on an `Int` key becomes
keyed. That changes fork #1 and is recorded as such in the changelog.

**D2 — Seek on the full key and check the rest (T2).** For a positive join on
a plain (non-temporal) stored relation, compute once, in one function used by
both dispatch (`ra.rs:2683`) and `::explain` labelling (`ra.rs:2584`):
`seek_len`, the length of the leading run `0..n` among the sorted right-side
join positions, cut at the key length. If `seek_len` equals the key length,
use a point lookup: build the key from the run positions only, and check every
other join pair on the found row (`point_lookup_join` already does the check).
If the positions are exactly `0..n`, nothing changes. Otherwise keep
`materialized_join`. Inside `prefix_join`, the point-lookup branch is taken when
`seek_len` equals the key length, not when the number of positions reaches it,
and the bounds slice starts at `seek_len`. `::explain` keeps
`stored_prefix_join` and lists the checked pairs in `joins_on`. Validity and
bitemporal relations, and all negated joins, keep today's gates in batch 1.

**D3 — Variable equalities through the same mechanism (T3).** Extend D1's
conversion to `eq(u, x)` where `x` is a variable: it becomes the non-constant
unification `u = x`, hoisted, under D1's conditions 3–5 with the declared type
non-numeric (numeric and `Any` columns are left alone). `well_order_body`
already holds a non-constant unification until `x` is bound
(`reorder.rs:207-213`, `:346-351`), so it lands after `f[x]` and before the
stored atom, which then seeks on `u`. If `x` is bound only after the stored
atom, the unification lands after it and compiles to today's filter. `u` must
be bound by a positive stored atom (`NormalFormAtom::Relation`); a variable
that appears only in a negated atom is not rewritten, so the query still
fails with `eval::unsafe_negation`.

**D4 — No switch.** Results are unchanged by construction (each rewrite is
restricted to cases where `op_eq` and storage identity agree), so there is no
`:pushdown off` option. `:reorder written` continues to control only the join
reorder; D0, D1 and D3 apply in both modes.

## Invariants

1. Every rewrite returns exactly the rows the unrewritten plan returns, on all
   backends, including for `Int`/`Float` cross-type values and `Null`.
2. A query that compiled before compiles after; a query that failed with an
   unbound-variable or unsafe-negation error still fails.
3. No rewrite introduces a `stored_mat_join` that the unrewritten plan did not
   have.
4. No seek prefix includes a validity or transaction-time column.
5. The `::explain` label of a stored join names the operator that runs.
6. Plans stay stat-free and deterministic.

## Acceptance tests

- **Plan shapes** (SQLite, new tests in the `planner_shape.rs` style, empty
  relations), asserting the `op` and `joins_on` columns: T1 (also with
  `:limit 1` and `:reorder written`), T2 and T3 compile to a point lookup.
  Negative shapes keep today's plan: `=` and `==` on a value column (streaming
  filter, no `stored_mat_join`), a three-relation body with a trailing `=` on a
  variable an earlier keyed join already binds, a partial key run with a
  value position (`materialized_join`), a temporal relation, a negated atom.
  `planner_baseline.json` is expected to stay unchanged; any change is reviewed.
- **Result equivalence** on mem, SQLite and RocksDB, for each shape: string
  keys; `Int` and `Float` keys with matching and cross-type constants; `Null`
  values; composite keys of two and three columns joined on `{0, 2}` and
  `{0, 3}` (these fail on a naive gate change); a variable also bound by a
  derived rule with a cross-type constant (the magic-set case); validity and
  bitemporal relations; a negated atom.
- **The numeric fence**: `t = 5.0` and `t == 5.0` on an `Int` column still
  return the `Int(5)` row; `t = 5` on an `Int` column becomes keyed.
- **MindGraph's lint fixtures** (`mindgraph-rs/scripts/fixtures/cozo-query-lint/`)
  replayed as plan-shape tests: every flagged line compiles keyed.
- **Benchmarks**, RocksDB and SQLite, warm, compile time excluded: the existence
  check `*node{uid}, uid = $u` at 10k and 1M rows, ratio under 2×; the T2 join
  with 10k left rows at 1M right rows, against today's plan; and adversarial
  shapes that must be no slower than today: a three-column key with a
  low-cardinality leading column and a residual on a value column, and the
  three-relation greedy shape.
- `cargo test -p mnestic --test fork_regressions --test matjoin_regression
  --test planner_shape` and the LSQB tier in `planner-guard` pass.

## Layering ruling

Engine only. MindGraph needs no change; its lint cases 2 and 3 can become
advisory once production runs the release, which is a MindGraph decision.

## Rejected alternatives

- **Seek on a partial key run and check the rest per row** (the first draft's
  D2). A per-left-row scan over a leading-key range is not output-sensitive:
  with few distinct leading values it costs left rows × range size, where
  `materialized_join` costs one sort and a binary search per row. Without
  statistics the engine cannot tell the cases apart. T2 needs only the full key.
- **Hoisting every qualifying equality** (the first draft's D1). On a value
  column it replaces a streaming filter with a full materialization, and in
  longer bodies it can reseed the greedy reorder onto non-key joins.
- **Substituting `x` for `u` in the stored atom with an alias** (the first
  draft's D3). The hoisted non-constant unification gives the same plan with
  machinery the planner already has.
- **Cost-based choice between prefix and materialized join.** The engine has
  no statistics, and the plans are stat-free by design. A full-key match is
  always a point lookup, which is what D2 adds.
- **Converting numeric equalities without the declared-type check.** Changes
  results for cross-type values (verified current state).
- **A warning instead of a rewrite.** Warnings move the burden to every
  consumer; the shapes are the natural way to write the queries.

## Open questions

1. Should D2 cover stored negation in the same batch? `StoredRA::neg_join`
   already seeks on the leading run and checks every pair, so it is a gate and
   label change.
2. Should D3 ship with D1 and D2, or wait for evidence that T3 still occurs
   after MindGraph's lint rewrites?
3. D1 narrows the existing `==` conversion. Is that acceptable as a fork #1
   change, or should `==` keep converting value columns for compatibility?
