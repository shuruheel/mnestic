## Problem and required distinction

A consumer reported that a rare-type vector query returned nothing after filtering
a global ANN prefix. This can happen when eligible vectors lie beyond the fetched
prefix, even when eligible rows exist. It does not by itself prove an engine defect:
the consumer query may need the engine's inherited HNSW `filter:` path.

Produce a domain-neutral fixture with primary key, type, text and vector columns.
Place at least k eligible vectors outside the negative control's global prefix;
include an empty type and a type with fewer than k rows. Preserve exact queries,
index options, seed and engine SHA. Keep embedding-model calls out of the reproducer.

## Questions to resolve in source and experiments

1. Where does inherited `filter:` apply: graph traversal, result eligibility, or
   both? Which expressions/bindings are supported, and what does `ef` bound?
2. Can the consumer express its predicate directly without changing scoring or
   performing an unbounded materialization? Does native hybrid search expose the
   necessary path, or is a scripted query required?
3. Does bounded widening recover eligible neighbors at the protocol's selectivity
   levels, and what work, latency and memory does it consume?
4. Are deadline and memory limits honored inside the relevant search loop? What
   diagnostics or partial results distinguish budget exhaustion from no matches?
5. Do updates/deletes and snapshot semantics preserve eligibility across both
   vector and FTS legs? Can repeated widening share one stable read snapshot?

Use CodeGraph first for the indexed engine source, then confirm behavior with
focused tests. Record verified semantics and unresolved questions; do not promote
a query option's name into a guarantee about its implementation.

## Experiment and acceptance

Follow the [E1–E3 protocol](0.19-measurement-protocol.md), including its exact
eligible oracle, global BM25 statistics, selectivity strata, seed pairing and
predeclared quality/resource thresholds. Compare:

- Global top-N followed by filtering (negative control).
- Inherited HNSW `filter:` at the fixed parameter sweep.
- The same path with bounded widening under one total deadline and stable snapshot.
- Exact search over eligible vectors (quality and small-subset cost reference).

Check all returned keys against eligibility. Include equal-distance ties, empty
sets, fewer-than-k results, repeated calls, upsert/delete, and budget exhaustion.
Do not require approximate search to equal the exact top-k on arbitrary data.
Use a separated, deterministic tiny fixture for exact correctness assertions;
measure recall on the larger workloads. Report both vector and fused results so
FTS cannot conceal a vector-path failure.

## Decision table

| Evidence | Outcome |
|---|---|
| Existing filter path meets quality and bounded-work goals | Publish the verified query pattern and consumer guidance; no new engine mechanism |
| Existing path needs bounded widening and it qualifies | Document the widening/snapshot/budget contract and an executable example; include an engine helper only if independently justified |
| Reproduced implementation defect in the existing path | Minimal regression fixture and scoped fix, with compatibility/resource review |
| Quality is adequate only with uncontrolled work, or required bounds cannot be verified | Record the failed gate and investigate a bounded alternative; do not claim success |
| Existing path fails and a new mechanism appears necessary | Prepare a separate implementation contract before choosing HNSW `candidates:` or another design |

A new contract must settle candidate representation and size limits, duplicate/
missing keys, predicate composition, metric/ranking semantics, snapshot/update
behavior, timeout/partial-result handling, estimated-memory and work bounds,
backend behavior, and Rust/Python exposure. It must include an API compatibility
assessment and measurable acceptance tests. No storage-format change is assumed.

## Release boundary and deliverables

Deliver a reproducible fixture, source-backed semantics, raw benchmark artifacts,
and a decision with a supported query example or an explicit unresolved limitation.
The fixture and decision are useful outcomes even when no new engine code ships.

A new mechanism enters 0.19 only if evidence, contract, tests, implementation and
review fit before the November 5 freeze. Otherwise schedule it independently;
retain the transaction/warning scope. A confirmed current correctness defect is
escalated in the release plan rather than hidden behind this optional-feature gate.

Do not claim consumer deployment or governance activation from an engine result.
The release plan tracks consumer compatibility separately.
