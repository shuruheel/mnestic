# 0.19 measurement protocol: E1–E3

Status: protocol prepared October 30, 2026; execution and results pending.
Owner: the 0.19 implementation/release owner. This document defines experiments,
not performance claims. The [release plan](0.19-planning.md) owns delivery scope.
Implementation and raw artifacts belong in `shuruheel/mnestic-benchmarks`.

## Reproducibility and baseline

Before timed runs, commit the harness and store a run manifest containing:

- Engine source SHA/tag, package version and artifact hash; harness SHA and diff
  status; exact dependency lock/freeze, Python/Rust versions and enabled features.
- OS/CPU/RAM, backend, database options, index parameters, concurrency, power mode,
  dataset/query hashes, random seeds, and exact commands/environment variables.
- Warmup/query order, process/rebuild boundaries, repetition count, time/resource
  ceilings, metrics definitions, and deviations from this protocol.

Use released `v0.18.0` as baseline and one immutable candidate SHA. Package them
into separate environments; do not resolve `mnestic>=0.8.2` afresh and assume it
selects the intended build. Never install the candidate over a baseline process.
Use equivalent build profiles/features. Run SQLite and RocksDB separately; report
backend differences without pooling. Check correctness on the tiny workload first.

Retain the existing small reference workload: 40,000 chunks, 10,000 entities,
50,000 edges, dimension 384, 1,000 queries, k=10, pool_n=100, graph_hops=2,
rrf_k=60, seed=1234. Verify these against the harness before executing; write any
necessary corrections into the manifest before timing. Add dimension 1,536 for
E3 and a filtered-vector sensitivity run. Synthetic embeddings support controlled
algorithm comparisons, not claims about real-world semantic relevance. Real
embeddings over synthetic words remain a latency sensitivity test only.

## E1: unfiltered reference and freshness

Measure decomposed three-signal retrieval and native fusion separately. Record
which signals actually participate, candidate depth, round trips, tie rules,
filters and fusion parameters. Never compare their latency while hiding a recall
or signal difference. Audit the harness/report against its current methodology:
the existing methodology's description of native scoring and the results table
must be reconciled before refreshing published claims.

For each build/backend/path, use three independent database builds with seeds
1234, 1235, 1236, paired between baseline and candidate. Preserve seed 1234 as the
historical reference. Run 100 untimed warmup queries followed by the fixed 1,000
query bank once per build; alternate baseline/candidate run order. Report each
run and pooled summaries, with bootstrap intervals resampled by query and build.
No concurrent benchmark processes. Cold measurements use fresh processes and are
labelled process-cold; do not claim cold OS caches unless controlled explicitly.

Report recall@10 against the exact oracle, returned count, empty-result rate,
p50/p95/p99 latency, throughput, build/ingest cost, disk size, peak process RSS,
timeouts/errors and per-query work counters when available. Keep process RSS
separate from engine-estimated statement memory. Timeout/error observations remain
in the denominator; report completed-query latency alongside failure counts.

For read-your-writes, use the small workload's 200 incremental writes. Record:

1. Write start to successful commit acknowledgement.
2. Commit acknowledgement to completion of the first immediate probe, per signal
   and fused path, including whether the expected row was returned.
3. Write start to that probe's completion, for the end-to-end cost.

Issue the first probe without sleep or retries. A miss stays a first-probe miss.
If measuring eventual visibility, report a separate polling experiment with its
poll interval and 5-second censoring deadline. Never substitute polling success
for first-probe success. Choose unique exact-match probes and check visibility
with exact/index reads as well as ANN top-k: ANN omission alone does not establish
that committed data is absent. Confirm rollback produces no visible mutation.

## E2: filtered retrieval

Use the [investigation brief](0.19-filtered-vector-investigation.md) for path
selection and decisions. Extend the query bank with eligibility selectivities of
100%, 10%, 1%, and 0.1%, plus empty and fewer-than-k eligible sets. Generate both
randomly assigned types and adversarial types concentrated outside the global
nearest-neighbor prefix. Store eligible primary keys with the fixtures.

The exact oracle first restricts the vector universe to eligible keys, then ranks
by the configured metric. FTS uses eligible keys before top-k with corpus-global
BM25 statistics, matching the existing candidate-aware FTS contract. Fuse eligible
component lists with fixed RRF and deterministic tie-breaking. Evaluate vector-only
and vector+FTS separately; do not compare two-signal results with the three-signal
historical oracle. If adding a graph leg, restrict its eligible output explicitly.

For positive truth sets, recall is intersection size divided by min(k, truth size).
For empty truth, recall is N/A and returning no rows is a separate correctness
check. Record ineligible rows and duplicate keys as correctness failures. Report
per-selectivity metrics; an overall average cannot conceal rare-type failures.

Run the post-filtered global ANN prefix as a negative control, inherited HNSW
`filter:`, and bounded widening of that path. Use an exact eligible-vector scan
as a quality/reference control. Record actual candidate/visit counts when
instrumentation permits. An `ef` parameter is not proof of a strict visit cap.

## E3: literal versus parameter costs

Use the same numerical vector and query semantics in each pair. Include dimension
384 and 1,536, one query and three-query request shapes, repeated and changing
vectors, and both SQLite/RocksDB. Require equal results before interpreting timing.
Measure client serialization, parameter construction, engine-call wall time, and
parse/plan/evaluation spans where instrumentation permits. Do not label the
literal-minus-parameter difference pure parse time: binding and serialization
also differ. Use a minimal-result query to expose overhead and a representative
retrieval query to measure its share of total cost. Reuse the E1 repetitions.

Publish parameter-binding guidance with executable examples. Investigate plan
caching further only if directly measured residual parse/plan work after binding
is at least 10% of request time and 1 ms at a documented high-frequency workload.
Without phase instrumentation or a real call-frequency profile, record an open
question rather than asserting that this gate passed. A cache is outside the
committed 0.19 implementation scope.

## Predeclared decision rules

These are engineering investigation thresholds, not product SLAs or exact-ANN
promises. Freeze them in the manifest before runs. Changes require a dated reason
and a new experiment identity; preserve unfavorable results from earlier runs.

- No ineligible results, duplicate keys, committed-data loss, or rollback leakage.
- On unchanged paths, a candidate loss exceeding 1 percentage point in mean
  recall, any new deterministic wrong-result case, or p95 slowdown exceeding both
  10% and 1 ms triggers investigation. Reproduce once under matched conditions;
  fix it, remove the optional change, or record an explicit release-owner decision
  with the tradeoff. These are review triggers, not proof that smaller losses are safe.
- For E2, target mean vector recall@10 >= 0.95 and empty-result rate <= 1% where
  at least k eligible rows exist, separately at each positive selectivity. Tiny
  exact fixtures must pass their deterministic assertions independently of averages.
- E2 exploration permits at most five attempts at ef=100, 200, 400, 800, 1600,
  with one 250 ms total query deadline across attempts, not a rearmed per-attempt
  timeout. Record effective engine options and whether interruption is cooperative.
  Assess a 64 MiB estimated statement budget where supported; measure peak RSS
  separately. Unsupported/unverifiable bounds are an investigation outcome, not a pass.
- Compare filtered-path cost with exact eligible scanning and report the tradeoff;
  reaching the quality threshold with uncontrolled work does not qualify the path.
- E3 cannot justify a cache based solely on artificial parse-only microbenchmarks.

Do not tune only the candidate. Publish the baseline and candidate parameter
sweeps and quality/cost frontier. Resource-cap exhaustion must be distinguishable
in the experiment from a genuinely empty eligible set.

## Artifacts and completion

Retain raw per-query records, manifests, oracle checks, dataset hashes, commands,
resource observations, confidence intervals, and unsuccessful runs. Each E1–E3
record states the question, result, limitations, and decision. Link artifacts
from the release-readiness record. Refresh benchmark `docs/RESULTS.md` only from
verified artifacts; preserve the old report with its original date/provenance.
New cross-engine rankings require fresh comparable competitor runs. The 0.19 gate
requires the paired Mnestic comparison, not a new broad competitive benchmark.

If a bounded run cannot complete by scope freeze, report the failure and replan
explicitly; do not silently shrink the workload or present partial runs as complete.
