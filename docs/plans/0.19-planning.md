# Mnestic 0.19 planning

Updated October 30, 2026 following the owner-directed 0.19 planning discussion.
This record supersedes the September 6 selection order and carries forward the
October 27 measurement priorities. Scope preparation is authorized; completion
and release readiness must be demonstrated by the evidence below.

**Provisional target: Thursday, November 12, 2026. Scope freeze: November 5.**
The target assumes roughly one focused engineering week across the two-week window.
Confirm feasibility after the first measurement pass. If correctness or package
validation misses the gate, use November 19 as the next checkpoint with scope
still frozen; the calendar never overrides a failed gate.

E1–E3 follow the [measurement protocol](0.19-measurement-protocol.md).
E2 follows the [investigation brief](0.19-filtered-vector-investigation.md).
Benchmark artifacts belong in the public `shuruheel/mnestic-benchmarks` repository;
engine contracts and release decisions belong here. Measurement and guidance are
release deliverables even if they establish that no engine change is needed.

A filtered-search change may enter 0.19 only when the existing path fails the
predeclared gate, a bounded contract and acceptance tests are ready, and the
implementation can clear review before November 5. Otherwise record the evidence
and schedule the mechanism separately. A confirmed current corruption, security,
or wrong-result defect takes precedence and may require revisiting scope/date.

## Existing 0.19 commitment

Remove the temporary `parser.string_decoding_changed` warning as promised in the
[0.18 migration notes](../../CHANGELOG-FORK.md) and
[string-literal contract](../specs/string-literals.md). Preserve the decoding semantics,
regression tests and migration guidance. This is not a new parser redesign.

## Warning-removal acceptance

- Preserve quoted/raw-string parsing semantics and the existing correctness tests.
- Remove only the temporary diagnostic and assertions that require its emission;
  keep coverage for warning routing/draining using another appropriate diagnostic.
- Before removing it, run representative consumer migrations/query builders on
  released 0.18 with quotes, backslashes, slashes, whitespace and Unicode. Assert
  expected results and no migration warnings for corrected builders; drain after
  each fixture. Keep fixtures that demonstrate the old warning separately.
- Run the same result/error assertions on the candidate. Absence of a diagnostic
  removed by design is not migration evidence. Retain an isolated 0.18 fixture/job
  until the consumer migration audit is complete.
- Update the string-literal contract and release notes to say which diagnostic
  was removed and where the permanent migration guidance lives.

## Deferred scope

HNSW verifier/repair, Arrow export, quantization, SQLite layout changes, schema
migration tooling, ULID ergonomics, phrase-query extensions, plan caching and
system-versioning redesign are not committed to 0.19. Existing evidence gates
remain in force. Temporary-relation diagnostics follow E1–E4 and require agreed
warning behavior before implementation.

## Demand-gated system-versioning integration

Recorded 2026-09-07 under MindGraph adoption B-T2 / D2. Evaluate an indexed
current-state view alongside commit-stamped history, with defined current-side
trigger/projection behavior, history retention access paths, a history-preserving
supported backup/restore contract, and reversible enable/disable semantics.
Preserve snapshot consistency, crash recovery, erasure and existing non-temporal
query behavior.

Activation: a MindGraph pilot relation in production for at least 30 days with
system-time reads answering a named customer question, or a named external TxTime
user requiring indexed current reads. This is a feasibility proposal, not a 0.19
build commitment. Current/history separation is an option to evaluate, not a
prescribed engine architecture. No MindGraph pilot is authorized by recording
this item: a named consumer and accepted recovery contract are prerequisites.

release checks and current-main CI do not validate a future candidate.

- [ ] Pass CI, including default/SQLite and RocksDB governed-transaction tests,
      commit-failure hooks, minimal-feature coverage and blocking clippy.
- [ ] Complete the transaction contract's release checklist and warning-removal checks above.

      verifying stored data, indexes and representative query results. Retain earlier

- [ ] Verify downstream compile/query compatibility at an immutable engine pin;
      record host-governance activation separately from engine package availability.
- [ ] Synchronize changelog, root and registry readmes, Python metadata/lockfile,
      roadmap and workspace version inventory; check version consistency.
- [ ] Complete a separate patch review for correctness, compatibility, resource limits,
      and claims. Resolve findings or remove the affected optional slice before readiness;
      optional feature additions must have cleared initial review before scope freeze.
- [ ] Record the readiness decision against the final candidate SHA.

After publication, verify Rust/Python registry versions, artifact provenance and
the GitHub release separately, and append that evidence to the delivery record.

The bridge remains at 0.1.12 unless a reviewed bridge change requires a new version;
if it changes, publish `mnestic-rocks` before `mnestic`. Do not infer storage-format
compatibility solely from an unchanged version number. Release notes must identify
the native-Rust scope of governed transactions and cooperative cancellation limits.
